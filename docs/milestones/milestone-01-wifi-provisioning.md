# Milestone 01 — ESP32 Wi-Fi Provisioning

**Status:** Complete

## Objective

Enable the ESP32 to connect to configurable Wi-Fi without requiring the firmware to be reflashed whenever the network changes.

## Why

A real IoT device cannot assume that its Wi-Fi SSID and password are known at firmware-build time. The device therefore needs a provisioning mechanism.

## Previous state

The ESP32 initially connected using Wi-Fi details embedded in the firmware. We then introduced WiFiManager so the credentials could be configured through a temporary device-hosted portal.

## Current architecture

```text
Normal startup
    |
    v
WiFiManager
    |
    +---- saved credentials ----> connect as Wi-Fi station
    |
    +---- BOOT held 5 seconds --> ESP32-Setup AP
                                      |
                                      v
                              192.168.4.1 portal
                                      |
                                      v
                              select/configure Wi-Fi
                                      |
                                      v
                              connect + persist
```

## Components

- ESP32 DevKit
- Arduino IDE
- Arduino C++ firmware
- WiFiManager library
- BOOT button on GPIO0
- Wi-Fi access point/hotspot

## Implementation

The firmware configures GPIO0 as an input with an internal pull-up. A pressed BOOT button reads `LOW`.

A continuous loop measures how long the button remains pressed. A duration of five seconds triggers Wi-Fi provisioning.

Normal Wi-Fi startup uses the saved WiFiManager credentials. WiFiManager is configured with a 10-second connection timeout.

## Provisioning sequence

1. ESP32 starts.
2. WiFiManager attempts to use saved Wi-Fi credentials.
3. During normal operation, the ESP32 joins the configured network as a Wi-Fi station.
4. The user holds BOOT for five seconds.
5. Firmware detects the long press on GPIO0.
6. WiFiManager starts the temporary `ESP32-Setup` access point.
7. The configuration portal is available at `192.168.4.1` while the device is in provisioning mode.
8. The user selects a Wi-Fi network and supplies its credentials.
9. ESP32 attempts the new connection.
10. On successful connection, WiFiManager persists the configuration and exits the portal.

## Artifacts

### Firmware

**Location:** `firmware/esp32/wifi_provisioning/wifi_provisioning.ino`

**Generated by:** Developer using Arduino IDE.

**Consumed by:** ESP32 firmware runtime.

### Wi-Fi credentials

**Location:** WiFiManager's ESP32 persistent configuration storage.

**Generated by:** WiFiManager during successful provisioning.

**Consumed by:** WiFiManager during subsequent startup.

The actual Wi-Fi password is intentionally not stored in this repository.

## Who trusts whom?

No certificate trust relationship exists in this milestone.

The current trust model is only the local Wi-Fi configuration process. Certificate-based device identity is a future milestone.

## Security considerations

- Wi-Fi credentials must not be committed to Git.
- The provisioning AP is currently a learning-stage mechanism and is not yet protected by a production-grade onboarding identity.
- The configuration portal is HTTP-based in this learning milestone.
- Production device provisioning will require stronger controls and will be addressed in later security milestones.

## Configuration changes

- WiFiManager added to the firmware.
- Wi-Fi connection timeout set to 10 seconds.
- GPIO0/BOOT configured as `INPUT_PULLUP`.
- Five-second BOOT long press added as the provisioning trigger.

## Testing procedure

1. Upload firmware without holding BOOT.
2. Open Serial Monitor at 115200 baud.
3. Verify the ESP32 connects using saved Wi-Fi credentials.
4. Press and hold BOOT for five seconds.
5. Verify `ESP32-Setup` appears.
6. Connect to the temporary AP.
7. Open the configuration portal if it does not open automatically.
8. Select the target Wi-Fi and submit its credentials.
9. Verify successful connection and a DHCP address.
10. Reboot the ESP32 without reflashing.
11. Verify it reconnects using the persisted credentials.

## Actual result

The BOOT button was verified to be GPIO0.

The tested provisioning flow produced:

```text
BOOT held for 5 seconds!
Starting Wi-Fi configuration...
StartAP with SSID: ESP32-Setup
AP IP address: 192.168.4.1
Starting Web Portal
Connecting to NEW AP
Connect to new AP [SUCCESS]
Got IP Address: 10.73.214.139
config portal exiting
```

The ESP32 successfully connected to the configured phone hotspot and received the DHCP address `10.73.214.139`.

A connection attempt initially failed and then succeeded on retry. The WiFiManager connection timeout was subsequently configured to 10 seconds.

## Problems encountered

### BOOT long press initially did not work

The first implementation checked GPIO0 only during `setup()`. Pressing BOOT after startup was therefore not detected.

**Correction:** button state is now monitored continuously in `loop()` and the five-second duration is measured there.

### WiFiManager timeout placement compilation error

A call to `wifiManager.setConnectTimeout(10)` was initially placed at global scope.

**Correction:** method calls must execute inside a function such as `setup()`. The timeout configuration was moved into `setup()`.

## Decisions

### Use BOOT as the Wi-Fi provisioning trigger

The board has no separate Wi-Fi reset button. GPIO0/BOOT provides a convenient physical recovery mechanism without adding hardware.

### Five-second long press

A long press reduces the chance of entering provisioning mode accidentally.

### Do not erase credentials immediately

The BOOT action means **enter Wi-Fi reconfiguration**, not blindly erase stored credentials. New credentials are supplied through the provisioning process.

## What you should now understand

- The ESP32 can join an existing Wi-Fi network without Internet being required for local communication.
- The ESP32 can temporarily become an access point for configuration.
- `192.168.4.1` is the ESP32's temporary provisioning address.
- GPIO0 is the BOOT button on this board.
- A five-second press is a firmware-defined provisioning trigger; it is not a special Wi-Fi feature of GPIO0.
- Wi-Fi provisioning is separate from device authentication and certificates.
