# Milestone 02 — Private IoT Certificate Authority

## Status
In progress — Root CA generated, inspected, and cryptographically verified

## Objective
Create a private Certificate Authority (CA) for the CognixVision IoT lab so that device certificates can later be issued and verified without depending on a public CA.

## Why we are doing this
In the previous milestone we solved Wi-Fi provisioning. The next security layer is device identity. A device certificate will eventually allow the platform or MQTT broker to authenticate an ESP32 using mTLS.

We will first create and understand our own CA locally. This isolates the PKI concepts from AWS, MQTT, and the backend and lets us see exactly what each artifact does.

## Connection to the previous milestone
Milestone 01 established network connectivity and Wi-Fi provisioning. Milestone 02 adds the identity layer:

```text
ESP32
  ↓

  ↓

  ↓

```

## Important terminology — simple first

- **Private key:** a secret cryptographic key. It must be protected.
- **Public key:** the matching non-secret key. It can be shared.
- **Certificate:** a signed statement binding an identity to a public key.
- **CA (Certificate Authority):** an entity that signs certificates so others can establish trust in them.
- **Root CA:** the top-level CA whose certificate is trusted directly.
- **Self-signed certificate:** a certificate whose signature is made using the private key corresponding to the public key inside the same certificate.
- **Trust store:** a collection of trusted CA certificates used to decide whether a certificate chain is trusted.

Technical relationship:

```text
CA private key
      │
      ├── signs ──────────────┐
      │                       ▼
      │                 Root CA certificate
      │                       │
      │                       └── contains CA public key
      │
      └── corresponding public key
```

### Why the CA needs a public key

A CA has a public/private key pair. We did not create a separate `.pub` file because the public key can be derived from the private key and is included in the CA certificate.

The private key signs certificates. The corresponding public key allows others to verify those signatures.

## Commands used

### Verify OpenSSL

```powershell
openssl version
```

### Generate the Root CA private key

```powershell
openssl genrsa -out cognixvision-root-ca.key 4096
```

### Verify the private key without printing it

```powershell
openssl rsa -in cognixvision-root-ca.key -check -noout
```

Expected result:

```text
RSA key ok
```

### Generate the self-signed Root CA certificate

```powershell
openssl req -x509 -new -key cognixvision-root-ca.key -sha256 -days 3650 -out cognixvision-root-ca.crt
```

### Inspect the Root CA certificate

```powershell
openssl x509 -in cognixvision-root-ca.crt -text -noout
```

### Verify the Root CA certificate

```powershell
openssl verify -CAfile cognixvision-root-ca.crt cognixvision-root-ca.crt
```

Expected result:

```text
cognixvision-root-ca.crt: OK
```

## What the certificate inspection showed

The generated certificate has the following important properties:

- X.509 Version 3.
- Signature algorithm: `sha256WithRSAEncryption`.
- Issuer and Subject are the same: `C=IN, ST=Kerala, L=Kochi, O=CognixVision, OU=IoT, CN=CognixVision Root CA`.
- Validity is approximately 10 years, from August 2026 to August 2036.
- Public-key algorithm: RSA.
- Public-key size: 4096 bits.
- `Basic Constraints` is critical and contains `CA:TRUE`.
- A Subject Key Identifier is present.

The matching Issuer and Subject demonstrate that this is a self-signed root certificate. `CA:TRUE` identifies it as a CA certificate rather than an end-entity/device certificate.

## Who trusts whom?

The Root CA certificate is the trust anchor:

```text
Future verifier
      │
      │ trusts
      ▼
Root CA certificate
      │
      │ will eventually validate
      ▼
Device certificate
```

The CA private key is **not** distributed to devices or application servers merely to establish trust.

## Security considerations

- The CA private key is the most sensitive artifact created in this milestone.
- It must not be committed to Git.
- It must not be copied to the ESP32.
- It must not be placed in the application repository.
- The root CA certificate is public trust material and can later be distributed to systems that need to verify certificates issued by this CA.
- This is a development/lab CA, not a production PKI.

## Decisions made

### Use a private lab CA first
We will create our own CA before introducing a public CA or AWS IoT PKI. This makes the certificate chain and trust model observable and understandable.

### Keep CA secrets outside Git
The CA private key is intentionally excluded from the repository. Git will contain documentation and safe public metadata only.

### Do not store a separate CA public-key file
The public key is mathematically derived from the private key and is carried inside the Root CA certificate. A separate public-key file is unnecessary for the current workflow.

### Do not expose machine-specific paths in project documentation
Local filesystem paths are represented using `<local-pki-directory>` so the documentation remains portable across machines and users.

## What you should now understand

- A CA has a **private/public key pair**.
- The private key is used to **sign** certificates.
- The public key is used by others to **verify** those signatures.
- A Root CA certificate is normally self-signed.
- `Issuer = Subject` is an important indicator of the self-signed root relationship.
- `CA:TRUE` tells certificate-processing software that this certificate represents a CA.
- The CA certificate contains the CA public key; a separate public-key file is not required.
- Certificate verification can happen locally. The CA does not need to be contacted each time a certificate is validated.
- `cognixvision-root-ca.crt: OK` means OpenSSL successfully verified the certificate using the specified CA file as its trust anchor.
