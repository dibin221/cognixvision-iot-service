## Important terminology — simple first

- **Private key:** a secret cryptographic key. The owner proves possession of it. It must be protected.
- **Public key:** the matching non-secret key. It can be shared.
- **Certificate:** a signed statement binding an identity to a public key.
- **CA (Certificate Authority):** an entity that signs certificates so others can establish trust in them.
- **Root CA:** the top-level CA whose certificate is trusted directly.
- **Trust store:** a collection of trusted CA certificates used to decide whether a certificate chain is trusted.

Technical relationship:

```text
Private key ──mathematically related──> Public key
                                      │
                                      ▼
                              Device certificate
                                      │
                              signed by the CA
                                      │
                                      ▼
                                  Root CA
```

### Why the CA needs a public key even though we generated only a private-key file

A CA also has a public/private key pair. We have **not created a separate public-key file** because it can be derived from the private key when needed. OpenSSL will use the private key to create the CA certificate, and that certificate contains the CA's public key.

The resulting trust model will therefore be:

```text
             CA key pair
                 │
        ┌────────┴────────┐
        │                 │
   Private key        Public key
   🔐 secret          shareable
        │                 │
        │ signs           │ included in
        ▼                 ▼
                    Root CA certificate
                         📜
```

The important distinction is that **the public key is not unnecessary**. It is necessary for verification. We simply do not need to manage it as a separate file at this stage.

## Security considerations

- The CA private key is the most sensitive artifact created in this milestone.
- It must not be committed to Git.
- It must not be copied to the ESP32.
- It must not be placed in the application repository.
- The root CA certificate is public trust material and can later be distributed to systems that need to verify certificates issued by this CA.
- This is a development/lab CA, not a production PKI.

## Decisions made

### Use a private lab CA first
We will create our own CA before introducing a public CA or AWS IoT PKI. This makes the certificate chain and trust model observable and understandable.

### Keep CA secrets outside Git
The CA private key is intentionally excluded from the repository. Git will contain documentation and safe public metadata only.

### Do not store a separate CA public-key file yet
The public key is mathematically derived from the private key and will be represented in the Root CA certificate. A separate public-key file is unnecessary for the current workflow.

## What changed from the previous milestone

Milestone 01 provided network connectivity and Wi-Fi provisioning. Milestone 02 has now created the first cryptographic identity artifact: the CA private key.

## What you should now understand

- A CA has a **key pair**, not just a private key.
- The private key is used to **sign** certificates.
- The corresponding public key is used by others to **verify** those signatures.
- We do not need a separate public-key file because the public key can be derived from the private key and will be carried in the CA certificate.
- The CA private key is secret; the CA certificate/public key is intended to be shareable as trust material.
- A CA does not need to be contacted every time a certificate is validated. A verifier can validate a certificate locally using the trusted CA certificate and cryptographic signatures.
